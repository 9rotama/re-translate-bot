# ログ設計

この文書は[非機能要件](./non-functional.md)の「ログと監視」を満たすために、何をどう記録するかを定める。
個々のイベントを出す箇所は、各実装タスク（#31〜#36）で組み込む。

## 集め方

- Workers Logs で集める。開発用と本番で設定は同じにする。
- サンプリングはしない（`head_sampling_rate` は `1`）。呼び出しが少なく、間引くと失敗の記録まで落ちるためである。
- invocation logs は有効にする。CPU 時間の超過や `waitUntil` の打ち切りは Worker のコードからは記録できないためである。リクエストの本文が含まれないことを開発用 Worker で確かめ、含まれていたら無効にする。
- traces と Issues は無効にする。traces は Interaction のトークンを含む followup の URL を記録し、Issues は例外の message を集めるためである。

## 記録する内容

具体的なイベントと値は `src/log.ts` で定め、そこから生成した[ログのイベント一覧](./log-events.md)で読む。
一覧は CI で `src/log.ts` と照合するので、手で書き換えない。

イベントは次の方針で決める。

- 次の場面は必ず記録する：Interaction の受信、署名検証の失敗、翻訳の各段と全体それぞれの成功と失敗、followup の編集の失敗、D1 の失敗、想定していない例外。レート制限で断ったことも、制限を見直す材料として記録する。
- ログはイベント名を `event` に持つオブジェクトとして出す。値は数、列挙した文字列、言語コード、ギルド ID とチャンネル ID、例外の情報に限り、自由な文字列は持たない。
- レベルはイベントごとに固定する。利用者がエラーを目にした失敗を `error`、利用者への結果に響かない異常を `warn`、それ以外を `log` とする。
- 翻訳の失敗は、少なくとも無料枠の使い切りと時間切れをエラーの種類で見分けられるようにする。それらが増えた場合に、入力の上限やレート制限を見直すからである。
- 時間切れは、`waitUntil` が打ち切られる前に自前の期限で翻訳を止めて記録する。期限の値は #31 と #32 で決める。自前の期限が効かずに打ち切られた場合は、invocation logs の outcome にしか残らない見込みである。
- 受信と失敗のイベントには、ギルド ID とチャンネル ID を付ける。どちらも利用者を特定する情報ではなく、失敗の起きた場所を絞り込むのに使う。
- 例外の原因は、例外と cause の name と code、stack のうちコードの位置の行で切り分ける。
- D1 の失敗では、クエリの文字列を記録せず、どのクエリかを列挙で表す。クエリの文字列には、`sql.raw` などを通して入力が混ざりうるからである。

## 記録しない内容

原文、翻訳結果、ユーザー ID、Interaction のトークン、例外の message は記録しない。
stack も、message を含む行は記録しない。
これを次の方法で守る。

- ログは `src/log.ts` のログ関数からだけ出す。それ以外の場所で `console` を呼ぶコードは lint で落とす。
- ログ関数はイベントごとに決めた値だけを型と実行時の検査で受け付け、それ以外は出力しない。
- ギルド ID とチャンネル ID は、Interaction の決まった項目から取り出す関数を通した値だけを受け付ける。ユーザー ID も同じ形の文字列なので、形の検査だけでは取り違えを防げないからである。例外の情報も、例外から取り出す関数を通した値だけを受け付ける。
- fetch handler と `waitUntil` に渡す処理は、最も外側で例外を捕まえ、例外の情報だけを記録する。捕まえなかった例外は、Workers Logs が message と stack ごと記録するためである。

## 上限と保持期間

- 2026年12月1日からの無料プランでは、取り込みは1日 0.5GB まで、保持期間は7日である。上限に達するとその日の取り込みが止まり、00:00 UTC に再開する。超過分の費用はかからない。
- 1日の量は、`/rt` が無料枠で約70回に限られるので約1,000件、署名の不正なリクエストが無料プランのリクエスト数の上限まで来ても約20万件と見積もった。1件が 2.5KB 以下なら上限に収まる。1件の大きさは配備後に確かめる。
- 上限に達した日は残りのログが失われるが、利用者への影響はないので受け入れる。

## 調べ方

- 調査はダッシュボードの Workers Logs で行う。翻訳の失敗をエラーの種類ごとに数えるクエリなどを保存しておく。
- `wrangler tail` は、配備の直後にログが出ているかをその場で見るのに使う。
- 時間切れと無料枠の使い切りが増えていないかは、保守する人が本番への配備時と利用者から報告があったときに、直近7日分で確かめる。
